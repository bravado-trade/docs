The mempool feed is Bravado's **low-latency** fills stream. Settlements are decoded directly from the Polygon **public mempool**, so a fill reaches you **~1–2s before the venue's own real-time feed reports it** (measured against Polymarket RTDS: earlier on ~100% of trades, ~1.5–2s median). Every fill carries the full on-chain lifecycle — **pending → mined → settled**, and the negative states (**reverted / dropped / replaced**) — plus the **owner wallet (EOA)** behind the trading proxy.

<Info>
  The legacy connection at `wss://stream.bravadotrade.com/ws` requires a
  separately provisioned feed token. A Data API or Market Data HMAC key is not
  that token. The Console-managed connection is a separate rollout; see
  [access and authentication](#access-and-authentication). The public
  [Live Trades](/api/market-data/trade-feed) feed mirrors the venue's push feed and
  uses your Market Data credential; this feed adds the mempool lead, the settlement-truth
  lifecycle, and inline identity. Coverage today is Polymarket.
</Info>

<Note>
  This feed is served **directly from the feed edge** (`stream.bravadotrade.com`), not
  proxied through `partner-api.bravadotrade.com` like the other APIs. That is deliberate:
  an extra proxy hop would add relay latency and erode the mempool lead that is the whole
  point of this feed. Connect to the edge host directly.
</Note>

## Access and authentication

Use a key created under **WebSockets**, not the separate Data API, Market Data
REST, or Trade API products. A key display name can be customised; its product
and `stream.read` scope determine eligibility. Do not send the API key itself as a feed bearer token. There are two
connection contracts, and the token must match the socket:

| Connection | Credential | Destination |
| --- | --- | --- |
| Legacy partner feed | Provisioned Ed25519 feed token | `wss://stream.bravadotrade.com/ws` |
| Console-managed fills · release candidate | Short-lived grant from signed `GET /mempool/token`, using a WebSockets key (`ws_stream`) with `stream.read` | `wss://stream.bravadotrade.com/ws/console` |
| Versioned lifecycle events · release candidate | Short-lived grant with explicit family permissions | [On-chain Events](/api/market-data/onchain-events) |

The Console-managed destinations are not generally available until coordinated
release validation is complete. A `404` on those paths is a deployment issue,
not a reason to rotate your API key. A `401` on the legacy socket means its feed
token is missing, expired or refused. Contact support with the destination and
error code; never send your API secret or token in a support message.

During the managed rollout, eligible organisations use
[**Mempool Fills** in Console](https://console.bravadotrade.com/products/mempool) to obtain access
without copying your API secret into the browser. Each reconnect obtains a fresh
grant; expiry closes the previous connection. Your subscription, scope, credits
and organisation permissions still apply. General plan prices do not override
an account-specific commercial agreement.

The HMAC path includes the canonical query: sort keys and percent-encode values
using RFC 3986. Use
[authentication examples](/authentication-examples) for the signing format.
The direct legacy example below continues to require its provisioned feed token.

## Connect

Pass an initial stream set and (optionally) a mode and replay count on the query string, and present your token as a `Bearer` header or a `?token=` parameter.

| Parameter | Values | Default | Meaning |
| --- | --- | --- | --- |
| `streams` | comma-separated stream names | — | Initial subscriptions (see [Streams](#streams)). |
| `mode` | `compact` \| `full` | `compact` | Frame detail (see [Modes](#the-fill-frame)). |
| `replay` | `0`–`500` | `0` | Recent fills to backfill per stream before live frames. |
| `sender_gate` | `on` \| `off` | `on` | `off` also delivers unverified and rejected pending transactions, tagged `sender_verified: false`. See [Sender verification](#sender-verification). |
| `pending_ttl` | Go duration, e.g. `10s` | server default | Drop your view of a pending fill sooner. Clamped to `2s`–`120s`. See [Client pending TTL](#client-pending-ttl). |

An invalid `sender_gate` or `pending_ttl` value is refused with HTTP `400` before the WebSocket upgrade.

```
wss://stream.bravadotrade.com/ws?streams=fills:polymarket:*&mode=compact&replay=100
```

<CodeGroup>

```javascript JavaScript
const token = "<your Bravado feed token>";
const ws = new WebSocket(
  `wss://stream.bravadotrade.com/ws?streams=fills:polymarket:*&mode=compact&token=${token}`
);

ws.onmessage = (e) => {
  const f = JSON.parse(e.data);
  if (f.type === "fill") {
    const leg = f.legs?.[0];
    console.log(
      `${f.status} ${leg?.side} ${leg?.shares} @ ${leg?.price_micro} ` +
      `(exact=${f.exact}, owner=${leg?.owner ?? "?"})`
    );
  }
};
```

```python Python
import json, asyncio, websockets  # pip install websockets

TOKEN = "<your Bravado feed token>"
URL = f"wss://stream.bravadotrade.com/ws?streams=fills:polymarket:*&token={TOKEN}"

async def main():
    async for ws in websockets.connect(URL, ping_interval=None):
        async for msg in ws:
            f = json.loads(msg)
            if f.get("type") == "fill":
                leg = (f.get("legs") or [{}])[0]
                print(f["status"], leg.get("side"), leg.get("shares"),
                      "@", leg.get("price_micro"), "exact=", f["exact"])

asyncio.run(main())
```

</CodeGroup>

<Warning>
  **All amounts are integer base units as decimal strings** — 6-decimal micro-USDC and
  6-decimal share units; `token_id` is an exact decimal string and `price_micro` is
  `usdc * 1e6 / shares`. Never parse these as floats.
</Warning>

## Streams

Subscribe to the firehose or narrow to a token, market, or wallet. One connection may hold **120** streams.

| Stream | Delivers |
| --- | --- |
| `fills:polymarket:*` | Firehose — every settlement. |
| `fills:polymarket:token:<decimal tokenId>` | Every fill touching that outcome token. |
| `fills:polymarket:market:<0x conditionId>` | Every fill in that market (both outcomes). |
| `fills:polymarket:wallet:<0x address>` | Every fill where the address is a maker, signer, on-chain taker, or the tx sender. |
| `ghost:polymarket:*` | Ghost fills — CLOB matches that never settled on-chain (also delivered on `fills:*`). |
| `stats:polymarket:latency` | Periodic feed-health stats: per-source win-rates, mempool-lead percentiles, coverage, and `sender_gate` counts (`mode`, `rejected`, `quarantined`, `unverified_expired`). |
| `market:polymarket:<decimal tokenId>` | Proxied Polymarket CLOB book/price/trade events (a convenience; one hop slower than connecting to the venue directly). |

<Note>
  A wallet matches a fill if it is any leg's maker or signer, any leg's on-chain taker,
  **or the transaction sender** — the operator rotates senders, so identity is never keyed
  on the sender alone. Related resolution and collateral streams
  (`resolutions:polymarket:*`, `collateral:polymarket:*`) and the
  [UMA resolution lifecycle](/products/uma-api) (`uma:polymarket:*`) are available over the
  same socket.
</Note>

## The fill lifecycle

A fill is not one event — it is a sequence of status transitions for the same transaction. This is the "did it actually settle?" signal no post-block feed can give you.

| `status` | Meaning | `exact` |
| --- | --- | --- |
| `matched` | Earliest signal — the venue's CLOB reported the off-chain match (`signal_source: "polymarket-clob"`), before a settle tx exists. | `false` |
| `pending` | The settle transaction is in the mempool (`signal_source: "mempool"`) — provisional amounts from calldata. | `false` |
| `mined` | Included in a block; exact amounts from the `OrderFilled` logs. Adds `lead_ms`, `block`. | `true` |
| `finalized` | The block reached finality. Carries `block`. | `true` |
| `reverted` | The transaction reverted on-chain — the fill did **not** happen. Carries no legs. | `true` |
| `dropped` | A pending/matched fill that never settled (`ghost: true` for an unmatched CLOB signal). | — |
| `replaced` | Superseded by another tx (same nonce). Carries `replaced_by`. | — |
| `reorged` | A mined block was reorged out. Carries `orphaned_block`; treat the tx as pending again. | — |

A `matched` signal **upgrades** to `pending` when the settle tx hits the mempool, or expires as a **ghost fill** if it never settles. Track a transaction by `tx_hash`, and **dedupe by `(tx_hash, status)`** — the same tx legitimately arrives once per transition.

## Sender verification

A `pending` frame is emitted only for a transaction whose sender holds the exchange OPERATOR role on-chain; third-party calldata wearing another wallet's name is rejected before it reaches any stream.

A pending transaction is calldata in the public mempool. Anyone can broadcast calldata that names any wallet as maker or taker, but only Polymarket's operators can actually settle a match on the exchange. Before a `pending` frame is emitted, we check the transaction sender against the exchange contract's `isOperator`. The check uses a cache of known operators, so it normally adds no delay. A sender we have not seen before is held for the on-chain check and then emitted with its original `ts_seen`. A pending transaction whose sender fails the check never reaches a default stream, the replay buffer, or a wallet stream.

`mined`, `finalized`, and `reverted` frames are unaffected: they come from block logs, which only the exchange can emit.

### Seeing unverified pendings (`sender_gate=off`)

Connect with `sender_gate=off` if you want the raw mempool view, including transactions whose sender is unverified or not an operator:

- Every `pending` frame, and the `dropped` or `replaced` frame that ends it, carries `sender_verified`. Unverified and rejected transactions carry `sender_verified: false`.
- Frames that a default (`sender_gate=on`) client would not receive carry **no `seq`**. The `seq` of the frames you share with gated clients stays gap-free.
- A transaction can arrive as `pending` with `sender_verified: false` and later again with `sender_verified: true` once its sender is verified. **Dedupe on `(tx_hash, status, sender_verified)`** on this connection.
- A rejected transaction ends with a `dropped` frame when its pending window expires.

```json
{"type":"fill","stream":"fills:polymarket:*","ts_seen":1756080000101,"ts_sent":1756080000102,
 "venue":"polymarket","exchange":"ctf_v2","tx_hash":"0x5c…","status":"pending","exact":false,
 "seen_pending":true,"sender_verified":false,"legs":[…]}
```

### Client pending TTL

By default a pending fill that never settles is closed by the server's `dropped` frame. Set `pending_ttl` (a Go duration such as `10s`, clamped to `2s`–`120s`) to close it sooner for your connection only. When your TTL elapses you receive a `dropped` frame with no `seq` and a `pending_ttl_ms` field set to the TTL that fired. The server's own later `dropped` for that transaction is suppressed for you, but a later `mined` or `replaced` frame is still delivered, so treat a TTL `dropped` as "stopped waiting", not "did not settle".

## Subscribe, unsubscribe, and replay in band

Beyond the query string, manage subscriptions over the socket. `replay=N` (0–500) backfills up to N recent fills per stream before live frames — so a reconnecting client recovers what it missed.

```json
{"type":"sub","streams":["fills:polymarket:token:7132…","fills:polymarket:*"],"replay":100}
{"type":"unsub","streams":["fills:polymarket:*"]}
{"type":"ping"}
```

## Filtered subscriptions

The stream names above route by a single dimension (token, market, or wallet). For a compound query — a wallet **and** a minimum size, or only settled fills in a set of markets — subscribe with a `filters` object instead. `op` is accepted as a synonym of `type`.

```json
{"op":"sub","streams":["fills:filtered"],"replay":100,
 "filters":{
   "token_ids":["7132…"],
   "condition_ids":["0x…"],
   "wallets":["0x…"],
   "min_size":"10",
   "min_notional":"5000",
   "status":["settled"]
 }}
```

The server replies with a `subscribed` ack carrying a `subscription_id`; every fill matching that subscription then arrives as a normal `fill` frame whose **`stream` is the `subscription_id`**:

```json
{"type":"subscribed","subscription_id":"sub_1","stream":"fills:filtered","filters":{…}}
```

### Filter fields

| Field | Matches | Notes |
| --- | --- | --- |
| `token_ids` | a leg's `token_id` | decimal uint256, as in the stream grammar |
| `condition_ids` / `market_ids` | a leg's `condition_id` | `0x` hex; the two fields are combined. A leg with no condition never matches |
| `wallets` | any wallet the fill touches | `0x` address (maker / signer / taker / sender), case-insensitive |
| `min_size` | a leg's `shares` | **shares, human units** (e.g. `"10"` or `"0.25"`); inclusive floor, compared exactly |
| `min_notional` | a leg's `usdc` | **USDC, human units** (e.g. `"5000"`); inclusive floor, compared exactly |
| `status` | the fill's lifecycle | tokens below |

`status` accepts the raw lifecycle tokens `pending`, `mined`, `reverted`, `finalized`, `dropped`, `replaced`, `reorged`, `matched`, plus three coarse aliases: **`settled`** = mined + finalized, **`reverted`** = reverted + dropped + reorged, **`pending`** = pending + matched.

### Logic and semantics

- **OR within a field, AND across fields:** `{"wallets":["A","B"],"min_notional":"5000"}` means `(A or B) AND notional ≥ 5000`.
- **Any-leg:** a settlement matches a token / wallet / `min_*` clause when **some** leg satisfies it (the same any-leg rule the stream names use). `status` is the settlement's single lifecycle state.
- **Amounts are exact integers** — compared against the fill's base-unit `shares` / `usdc`, never a float.
- **Multiple subscriptions per connection,** each with its own `subscription_id` and sequence; a fill matching several of your subscriptions arrives once per matching subscription. Filtered and stream-name subscriptions share the 120-per-connection cap.

### Managing a filtered subscription

Replace a subscription's filter (not reconnecting) or drop it by id:

```json
{"op":"update_subscription","subscription_id":"sub_1","filters":{"status":["settled"],"min_notional":"10000"}}
{"op":"unsub","subscription_id":"sub_1"}
```

`update_subscription` **replaces** the whole filter; the mempool feed does not take `add`/`remove` deltas (a delta is rejected with `INVALID_REQUEST` rather than silently ignored). Acks: `filter_updated`, `unsubscribed`. A bad filter returns `INVALID_FILTER` and leaves existing subscriptions untouched.

## Stream health and errors

A `status` frame is sent on subscribe and whenever a stream's health changes:

```json
{"type":"status","stream":"fills:polymarket:*","state":"live","since":1756080000000,"ts":1756080001234}
```

`state` is `live` or `degraded`; on `degraded`, `reason` is one of `upstream_disconnected`, `heads_stale`, `pending_silent`, `reorg_depth_exceeded`.

`error` frames carry a `code`: `TOO_MANY_STREAMS`, `BAD_STREAM`, `UNAUTHORIZED`, `SLOW_CONSUMER`, `BAD_MESSAGE`, and — for filtered subscriptions — `INVALID_FILTER`, `INVALID_REQUEST`, `UNKNOWN_SUBSCRIPTION`. A client whose send queue backs up is disconnected (`SLOW_CONSUMER`, close `1013`) rather than buffered — one slow consumer never delays another.
