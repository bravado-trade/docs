Use these routes for **backtests, audits, dashboards, anything older than the [live window](/api/analytics/uma-live)**. They read the complete record of Polymarket's UMA requests, proposals, disputes and settlements from the warehouse, with `from` / `to` ranges, keyset paging and `condition_id_source` provenance. Polymarket's UMA adapters and Protocol V2 are included, for `YES_OR_NO_QUERY` questions only. Other protocols that use the same oracle are not.

Read the [UMA overview](/products/uma-api) for the lifecycle, the status values and the [v2 breaking change](/products/uma-api#breaking-change-uma-api-v2). Read [coverage](/products/uma-api#coverage-and-history) for what each route covers.

<Info>
  UMA REST is part of the [Data API](/products/data-api): sign every request with your **Data API** credential (`analytics.read`) using [HMAC authentication](/authentication). Each successful response costs **1 API credit**, and the surface has its own per-key rate bucket. The UMA **WebSocket** is different: it stays on the Market Data credential (`stream.read`), see [UMA WebSocket](/api/market-data/uma-websocket). There is no separate UMA key.
</Info>

<Warning>
  A key that carries only `stream.read` can no longer read the UMA REST routes: they answer `403 INSUFFICIENT_SCOPE`. Use a Data API credential for REST and keep the Market Data credential for [`/uma/ws`](/api/market-data/uma-websocket).
</Warning>

## Make a signed request

Use your Data API key and secret from [Console](https://console.bravadotrade.com/keys). This example makes one REST request. A successful response costs **1 API credit**. Keep the secret on your server.

```javascript Node.js
import { createHash, createHmac } from "node:crypto";

const key = process.env.BRAVADO_API_KEY;
const secret = process.env.BRAVADO_API_SECRET;
if (!key || !secret) throw new Error("Set BRAVADO_API_KEY and BRAVADO_API_SECRET");

const url = new URL("https://partner-api.bravadotrade.com/uma/history/recent");
url.searchParams.set("stage", "settled");
url.searchParams.set("limit", "1");
url.searchParams.sort();
const timestamp = String(Date.now());
const requestTarget = url.pathname + url.search;
const bodyHash = createHash("sha256").update("").digest("hex");
const payload = [timestamp, "GET", requestTarget, bodyHash].join("\n");
const response = await fetch(url, {
  headers: {
    "X-Bravado-API-Key": key,
    "X-Bravado-Timestamp": timestamp,
    "X-Bravado-Signature": createHmac("sha256", secret).update(payload).digest("hex"),
  },
});
console.log("HTTP", response.status);
console.log(await response.json());
```

A `200` with `questions` confirms that your authenticated REST read succeeded. An empty `questions` array reports no matching records in the range. A `401` only confirms an authentication refusal, not a successful read of resolution data.

Base URL: `https://partner-api.bravadotrade.com`. Sign every REST request with HMAC, including its sorted query parameters. JSON. Ids are lowercase hex, `price_raw` is the exact 32-byte two's-complement `int256` word, and `payout` is an integer micro-USDC string.

The history routes serve the same v2 body as the [live routes](/api/analytics/uma-live), computed over the complete on-chain record rather than the retained live window. `pending` is always `[]` here, because history has no mempool view.

## `GET /uma/history/question`

The complete lifecycle of one question, in the v2 body.

```text
GET https://partner-api.bravadotrade.com/uma/history/question?id=<0x questionId>
```

<ParamField query="id" type="string" required>
  The `0x` 32-byte `question_id`. The `0x` prefix is optional.
</ParamField>
<ParamField query="from" type="string">
  Start of the search window: RFC3339, unix seconds or unix milliseconds. The question must have an event at or after it. Default: all history.
</ParamField>
<ParamField query="to" type="string">
  End of the search window: RFC3339, unix seconds or unix milliseconds. The question must have an event before it. Default: now.
</ParamField>

`from` and `to` select which questions match. They never truncate a lifecycle, so `status` and `outcome` always describe the current answer.

<ResponseField name="fold_version" type="string" required>Always `uma-lifecycle/2`.</ResponseField>
<ResponseField name="question_id" type="string" required>Hex question id (`keccak256` of the ancillary data).</ResponseField>
<ResponseField name="title" type="string | null" required>Market question, up to 256 bytes. `null` when the record carries no title.</ResponseField>
<ResponseField name="family" type="string" required>Requester family of the active request: `uma_ctf_adapter` (standard markets), `negrisk_adapter` (NegRisk markets), `legacy_v1`, `polymarket_v2` (Protocol V2), or `unknown`.</ResponseField>
<ResponseField name="condition_id" type="string | null" required>The CTF condition id, or `null` when it is not established. See `condition_id_source`.</ResponseField>
<ResponseField name="condition_id_source" type="string" required>How `condition_id` was established: `derived` (the adapter's own condition derivation, `keccak256(requester, question_id, 2)`, exact by construction and identical on the live routes), `negrisk_exact` (the exact NegRisk condition map, when that map is enabled on the server), `pv2_exact` (the Protocol V2 `request_id`), or `unknown`.</ResponseField>
<ResponseField name="condition_id_reason" type="string" conditional>Present when `condition_id_source` is `unknown`. Values: `not_in_condition_map`, `condition_map_unavailable`, `negrisk_map_unavailable` (the NegRisk exact map is not enabled on this server, or its table is not readable), `negrisk_not_in_map`, `ambiguous_negrisk_map`, `pv2_requests_unavailable`, `pv2_request_not_found`, `ambiguous_pv2_request`, `unsupported_family`.</ResponseField>
<ResponseField name="status" type="string" required>Stage of the active request over its whole lifecycle: `requested`, `proposed`, `disputed`, `settled`, or `unknown` (no oracle request is identifiable).</ResponseField>
<ResponseField name="active_request" type="object | null" required>The request with the highest `request_ts`. It decides `status` and `outcome`. `null` when `status` is `unknown`.</ResponseField>
<ResponseField name="active_request.requester" type="string">The requester address of the active request.</ResponseField>
<ResponseField name="active_request.request_ts" type="integer">The request key timestamp (unix seconds). It identifies the request. It is not the time of an event: use `block_ms` for that.</ResponseField>
<ResponseField name="active_request.origin" type="string">Why this request exists: `initial`, `dispute_reset`, `ignore_reset`, `re_request`, or `unobserved`. See [Origins](#origins).</ResponseField>
<ResponseField name="active_request.basis" type="string">`request_event` when the request's RequestPrice is in the record, or `stage_events_only` when the request is known only from its stage events.</ResponseField>
<ResponseField name="outcome" type="object | null" required>The active request's Settle. `null` until that request settles. A Settle of any other request never sets `outcome`.</ResponseField>
<ResponseField name="outcome.answer" type="string">`yes`, `no`, `50-50`, `too-early`, or `other`.</ResponseField>
<ResponseField name="outcome.price_raw" type="string">The exact 32-byte two's-complement `int256` settled price, hex.</ResponseField>
<ResponseField name="outcome.payout" type="string">Settled payout, integer micro-USDC string.</ResponseField>
<ResponseField name="outcome.request_ts" type="integer">The request key of the active request that this Settle closes.</ResponseField>
<ResponseField name="outcome.via" type="string">`dvm` when the active request was disputed and settled by UMA's vote, or `optimistic` when it settled without a dispute.</ResponseField>
<ResponseField name="outcome.settle" type="object">Where the Settle was mined: `block`, `block_ms`, `tx`, `log_index`.</ResponseField>
<ResponseField name="requests" type="array" required>Every oracle request of the question, ascending by `request_ts`. See [Requests](#requests) for the item fields. At most 50 requests are listed: the active one is always kept, and `coverage.truncated` is `true` when older requests were cut.</ResponseField>
<ResponseField name="pending" type="array" required>Always `[]` on history.</ResponseField>
<ResponseField name="updated_ms" type="integer" required>Block time (unix ms) of the latest mined event in the question's lifecycle.</ResponseField>
<ResponseField name="coverage" type="object" required>What the response is based on. Present on every response.</ResponseField>
<ResponseField name="coverage.source" type="string" required>`warehouse`.</ResponseField>
<ResponseField name="coverage.from_ms" type="integer" required>Unix ms of the earliest bound actually read for this question. Use it to know how far back the lifecycle was read.</ResponseField>
<ResponseField name="coverage.to_ms" type="integer" required>Unix ms of the end of the read, which is now.</ResponseField>
<ResponseField name="coverage.truncated" type="boolean" required>`true` when older requests were cut from `requests`.</ResponseField>

A `404` with code `not_found` means no event for that id exists in the window you requested.

### Origins

| `origin` | Meaning |
| --- | --- |
| `initial` | The first request of the question, with its RequestPrice in the record. |
| `dispute_reset` | Re-requested in the same transaction as a dispute of an earlier request. |
| `ignore_reset` | Re-requested after the adapter discarded a too-early settlement. |
| `re_request` | Any other re-request whose RequestPrice is in the record. |
| `unobserved` | Known only from its stage events; its RequestPrice is not in the record. |

Origin labels are exact when the lifecycle is read from the question's first event. The history routes widen the read to the start of history when needed, so the label is exact there.

### Requests

Each item of `requests` carries:

- `requester`, `request_ts` and `origin`, which identify the request.
- `request`: where its RequestPrice was mined, as `block`, `block_ms`, `tx` and `log_index`. `null` when the origin is `unobserved`.
- `proposals`, `disputes` and `settles`: the steps of that request, each with `block`, `block_ms`, `tx`, `log_index`, `price_raw`, `answer`, and `proposer` or `disputer` when known.
- A settle also carries `payout`, and `superseded: true` when it belongs to a request that is not the active one. A superseded settle never moves `outcome`.

## `GET /uma/history/market`

The same v2 body, looked up by the market's CTF condition id.

```text
GET https://partner-api.bravadotrade.com/uma/history/market?condition_id=<0x conditionId>
```

<ParamField query="condition_id" type="string" required>
  The `0x` 32-byte CTF condition id. The `0x` prefix is optional.
</ParamField>
<ParamField query="from" type="string">
  Pins the search window start: RFC3339, unix seconds or unix milliseconds. Default: all history for the market.
</ParamField>
<ParamField query="to" type="string">
  Pins the search window end: RFC3339, unix seconds or unix milliseconds. Default: now.
</ParamField>

`condition_id` is always the **real** condition id, including for NegRisk markets. The route answers in one of two shapes, both with HTTP `200`. A resolved answer carries the v2 body. An unknown answer carries the fields marked `shape="unknown"`. Check `condition_id_source` first: it is present in both shapes.

<ResponseField name="condition_id" type="string" required>The condition id you looked up, as the real id.</ResponseField>
<ResponseField name="condition_id_source" type="string" required>`derived`, `negrisk_exact` or `pv2_exact` on a resolved answer. `unknown` on an unknown answer, with the reason in `reason`.</ResponseField>
<ResponseField name="question_id" type="string | null" required>The question the market resolved through. `null` when no oracle request was tied to the market.</ResponseField>
<ResponseField name="fold_version" type="string" shape="resolved">Always `uma-lifecycle/2` on a resolved answer.</ResponseField>
<ResponseField name="title" type="string | null" shape="resolved">Market question, up to 256 bytes. `null` when the record carries no title.</ResponseField>
<ResponseField name="family" type="string" shape="resolved">Requester family of the active request. See [`/uma/history/question`](#get-/uma/history/question).</ResponseField>
<ResponseField name="condition_id_reason" type="string" shape="resolved" conditional>Not present on a resolved answer.</ResponseField>
<ResponseField name="status" type="string" shape="resolved">`requested`, `proposed`, `disputed`, `settled`, or `unknown`.</ResponseField>
<ResponseField name="active_request" type="object | null" shape="resolved">The request that decides `status` and `outcome`. See [`/uma/history/question`](#get-/uma/history/question).</ResponseField>
<ResponseField name="outcome" type="object | null" shape="resolved">The active request's Settle, `null` until it settles. See [`/uma/history/question`](#get-/uma/history/question).</ResponseField>
<ResponseField name="requests" type="array" shape="resolved">Every oracle request of the question. See [`/uma/history/question`](#get-/uma/history/question).</ResponseField>
<ResponseField name="pending" type="array" shape="resolved">Always `[]` on history.</ResponseField>
<ResponseField name="updated_ms" type="integer" shape="resolved">Block time (unix ms) of the latest mined event.</ResponseField>
<ResponseField name="coverage" type="object" shape="resolved">Present on a resolved answer, with `source` (`warehouse`), `from_ms`, `to_ms` and `truncated`.</ResponseField>
<ResponseField name="reason" type="string" shape="unknown">Why the market could not be tied to an oracle request. See [Unknown answers](#unknown-answers).</ResponseField>
<ResponseField name="searched_from_ms" type="integer | null" shape="unknown">The start of the window searched. Set for `no_stage_events` and `requester_family_mismatch`, and `null` for the other reasons.</ResponseField>
<ResponseField name="searched_to_ms" type="integer | null" shape="unknown">The end of the window searched. Set for `no_stage_events` and `requester_family_mismatch`, and `null` for the other reasons.</ResponseField>

### Unknown answers

When the market cannot be tied to an oracle request, the answer is an explicit unknown: HTTP `200`, `condition_id_source` set to `unknown`, and a `reason`. It is never an empty success and never a `404`. An unknown answer carries no `status`, `active_request` or `outcome`, so do not read it as an unsettled market.

```json Unknown example
{
  "condition_id": "0x…",
  "question_id": null,
  "condition_id_source": "unknown",
  "reason": "no_oo_request_found",
  "searched_from_ms": null,
  "searched_to_ms": null
}
```

| `reason` | Meaning |
| --- | --- |
| `no_oo_request_found` | No oracle request is tied to this condition id. |
| `negrisk_map_unavailable` | The id is not a standard or Protocol V2 market, and the NegRisk exact map is not enabled on this server. |
| `negrisk_not_in_exact_map` | The NegRisk exact map is enabled, and it holds no entry for this id. |
| `requester_family_mismatch` | A map entry names this market, but the question's requester is not the family that mapping requires. The entry is not served. |
| `no_stage_events` | The question was found, but no oracle events for it were found in the read. `question_id` is then set. |

## `GET /uma/history/recent`

Questions with proposal, dispute or settlement activity in a time range, most recent activity first, one entry per question, paged with a cursor.

```text
GET https://partner-api.bravadotrade.com/uma/history/recent?stage=settled&limit=100&from=1792000000
```

<ParamField query="stage" type="string">
  Filter on the question's `status` (the active request's stage over its whole lifecycle): `requested`, `proposed`, `disputed` or `settled`. Omit for all.
</ParamField>
<ParamField query="limit" type="integer" default="100">
  Questions per page, from 1 to 500.
</ParamField>
<ParamField query="from" type="string">
  Range start: RFC3339, unix seconds or unix milliseconds. Default: `to` minus 24 hours.
</ParamField>
<ParamField query="to" type="string">
  Range end: RFC3339, unix seconds or unix milliseconds. Default: now.
</ParamField>
<ParamField query="cursor" type="string">
  The `next_cursor` of the previous page. Treat it as opaque.
</ParamField>

<ResponseField name="questions" type="array" required>Question records, each in the v2 body of [`/uma/history/question`](#get-/uma/history/question). A question that cannot be read is listed with `status` `unknown`, `status_reason` `question_unreadable`, and `active_request` `null`, so the rest of the page is still served.</ResponseField>
<ResponseField name="count" type="integer" required>Records in this page.</ResponseField>
<ResponseField name="from_ms" type="integer" required>Resolved range start (unix ms).</ResponseField>
<ResponseField name="to_ms" type="integer" required>Resolved range end (unix ms).</ResponseField>
<ResponseField name="limit" type="integer" required>Page size applied.</ResponseField>
<ResponseField name="has_more" type="boolean" required>Whether another page follows the cursor.</ResponseField>
<ResponseField name="next_cursor" type="string | null" required>Pass as `cursor` to read the next page. `null` on the last page.</ResponseField>

The range is at most **7 days**. A wider one is refused with `400 range_too_large` rather than silently shortened, so page a long period with consecutive `from` / `to` windows.

Paging is keyset-based on the block time, block number and log index of each question's latest event in the range, so a page never repeats or skips a question. A page can hold fewer than `limit` questions when `stage` filters out candidates, and it can still carry `has_more: true` and a `next_cursor`. Keep paging until `has_more` is `false`.

Each question's lifecycle is read from up to 30 days before `from`. `coverage.from_ms` on each record states the earliest bound actually read for that question.

<Note>
  For stable paging, pin `to` (an explicit timestamp) on every page request. With the default `to=now` the window moves between requests, and a question can be skipped across a page boundary. Each response echoes the resolved `to_ms` so you can reuse it.
</Note>

## Errors

| Status | Code | Meaning |
| --- | --- | --- |
| `400` | `invalid_id` | `/uma/history/question`: `id` is missing, or is not a 32-byte hex id (the `0x` prefix is optional). |
| `400` | `invalid_condition_id` | `/uma/history/market`: `condition_id` is missing, or is not a 32-byte hex id (the `0x` prefix is optional). |
| `400` | `invalid_stage` | `/uma/history/recent`: `stage` is not one of `requested`, `proposed`, `disputed`, `settled`. |
| `400` | `invalid_limit` | `/uma/history/recent`: `limit` is not an integer from 1 to 500. |
| `400` | `invalid_from`, `invalid_to` | `from` or `to` is not RFC3339, unix seconds or unix milliseconds. |
| `400` | `invalid_range` | `from` is not before `to`. |
| `400` | `invalid_cursor` | `/uma/history/recent`: `cursor` is not a value returned as `next_cursor`. |
| `400` | `range_too_large` | `/uma/history/recent`: the range is wider than 7 days. Page with consecutive windows. |
| `404` | `not_found` | `/uma/history/question`: no event for that id in the window. |
| `401` | `INVALID_SIGNATURE`, `STALE_TIMESTAMP`, `INVALID_KEY`, `KEY_DISABLED` | Signature or key refused. See [HMAC authentication](/authentication). |
| `402` | | Credit allowance exhausted. See [API credits](/api-credits). |
| `403` | `INSUFFICIENT_SCOPE` | Your credential does not carry `analytics.read`. |
| `429` | `RATE_LIMITED` | Rate limit reached. Retry after a short wait. |
| `503` | `UMA_HISTORY_UNAVAILABLE`, `NOT_CONFIGURED` | The history store is unavailable or not configured. Retry after the `Retry-After` interval. |
| `500` | `internal` | An unexpected server error. Retry later. It is not an empty result and does not mean the question has no record. |
| `504` | `UPSTREAM_TIMEOUT` | The upstream read timed out. Retry, with a narrower range if the request was a range read. |

## Recover after a disconnect

After consuming the live [WebSocket](/api/market-data/uma-websocket), call `/uma/history/recent` with `from` set to your last event to recover the questions that changed while you were away, in order, with no gap. If the gap is longer than 7 days, page it with consecutive windows. For the lowest-latency reads of what is resolving right now, use the [live window](/api/analytics/uma-live) instead.
