<Note>Sign each request with a fresh HMAC signature. The cURL and HTTP header values below are placeholders, not reusable credentials. For runnable signing code, use [request signing examples](/authentication-examples). Python examples use the signed session from that page; Node.js examples use its `bravadoFetch` helper.</Note>


Returns the performance summary for a single wallet, including PnL, volume, position counts, streak data, and identity fields.

```text
GET https://partner-api.bravadotrade.com/trader-analytics/traders/{address}
```

### Path Parameters

<ParamField path="address" type="string" required>
  Polygon wallet address in `0x…` format. Case-insensitive.
</ParamField>

### Query Parameters

<ParamField query="window" default="all" type="string">
  Rolling time window. Accepted values: `1h`, `4h`, `24h`, `7d`, `30d`, `90d`, `365d`, `all`.
</ParamField>

<ParamField query="basis" default="net" type="string">
  `net` deducts fees from `realized_pnl` and `total_pnl`; `gross` adds fees back to report pre-fee figures **where the fees can be valued**. A `gross` request is declined, and `net` is served, for a wallet whose history holds any V1 share-denominated fee rows (those fees cannot be valued in USD, so a partial add-back would be wrong); the whole all-time add-back is declined, the V2 part included. Read the `basis` and `fees_basis` response fields to see what you actually got.
</ParamField>

<ParamField query="income" default="total" type="string">
  `total` returns a single `income` aggregate; `detail` expands into `maker_rebate`, `reward_income`, and `liquidity_reward`; `none` omits income fields.
</ParamField>

### Response

<ResponseField name="basis" type="string" required>
  The fee basis the served `realized_pnl`, `overall_pnl` and `total_pnl` actually carry: `net`, `gross` or `unknown`. It equals your `basis` parameter except where the service declined or neutralized it: a `gross` request that was declined reads `net` (`fees_basis` `v1_fee_unvalued`, or `unavailable_sub_day` on a fee-net venue); a `net` request served gross (a 1h/4h/24h window with no sub-day fee source, `fees_basis` `unavailable_sub_day`) reads `gross`; predict.fun always reads `net` (`fees_basis` `engine_net`); `unknown` is served only while a recompute holds the engine (`fees_basis` `recompute_in_flight`). Always present.
</ResponseField>

<ResponseField name="fees_basis" type="string" required>
  Which fees were deducted from, or added back to, `realized_pnl`: `all_time` (window `all`, the wallet's all-time fees deducted), `window_daily` (7d, 30d, 90d, 365d: the window's own fees deducted), `unavailable_sub_day` (1h, 4h, 24h: there is no fee source at that grain, so no fee adjustment is made and the figure keeps whatever fee state the rollup has; see `basis`), `none` (you asked for `gross` and nothing was deducted), `engine_net` (the engine's `realized_pnl` is already net of fees, so nothing was deducted here; always the value on predict.fun), `engine_gross` (you asked for `gross` and the fee was added back exactly), `v1_fee_unvalued` (you asked for `gross`, but the wallet has V1 share-denominated fee rows that cannot be valued in USD, so the add-back was declined and `net` is served), `recompute_in_flight` (a recompute holds the engine, so the fee subtraction was declined for every wallet; the raw engine figure is served and `basis` is `unknown`). Always present.
</ResponseField>

<ResponseField name="fees" type="string" required>
  The wallet's **all-time** fee total as an exact decimal string, at every `window`. It is a separate line, never netted into the figures above by this field. `total_fees` is an alias with the same value. The fee for the window you asked about is `windows.<window>.fees_paid`.
</ResponseField>

<ResponseField name="fees_scope" type="string" required>
  Always `all_time`: the time scope of `fees` and `total_fees`, whatever `window` you sent. Do not subtract a windowed `fees` from a windowed PnL; use `windows.<window>.fees_paid`.
</ResponseField>

<ResponseField name="active_positions" type="integer or null" required>
  Count of open positions worth at least $1, or whose value is unknown. This is a **snapshot** from the open-state rollup, refreshed about every 25 minutes. A live [`GET /positions?wallet=...&status=open`](/api/analytics/positions) read re-marks every position per request, so the two can differ by trades and price moves since the snapshot. `null` when the wallet's on-chain balances have not been indexed (`open_value_source` is `unknown_book_unseeded`) or its book is quarantined.
</ResponseField>

<ResponseField name="reference_engine" type="object">
  Present only for the 12 wallets in the PMWAS reference cohort, and only with `window=all`. It is the PMWAS reference engine's figure, shown for comparison. **It is not the served PnL**: `realized_pnl`, `total_pnl` and every other figure on this page come from the production engine for every wallet, cohort wallets included. The two engines are under reconciliation and disagree on most cohort wallets.
  <Expandable title="properties">
    <ResponseField name="total_pnl" type="string">Reference-engine total economic return in USDC, net of fees.</ResponseField>
    <ResponseField name="realized_pnl" type="string">Reference-engine net realized PnL in USDC.</ResponseField>
    <ResponseField name="batch_block" type="integer">Block of the reference batch the figures come from.</ResponseField>
    <ResponseField name="source" type="string">Always `pmwas_reference`.</ResponseField>
    <ResponseField name="status" type="string">Always `under_reconciliation`.</ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="recognized_capital"  type="string" required>
  USDC, exact 6-decimal string. Proceeds on shares whose cost basis is unknown, recognized as **capital** (PMWAS §7.7(b)): in-kind capital, **not** profit or loss, and never part of `realized_pnl`, `total_pnl` or any total. `"0.000000"` means nothing was recognized. `null` means unknown, never zero; see `recognized_capital_source`. Always present. All-time only: it equals the sum of `recognized_capital` over the wallet's rows in [`GET /positions`](/api/analytics/positions), and is `null` if any of those rows is `null`.
</ResponseField>

<ResponseField name="recognized_capital_source" type="string" required>
  Why `recognized_capital` is what it is. `fifo_fills` when it is a figure. When it is `null`: `pre_convention` (part of the wallet's records predate the convention), `window_unsupported` (`window` is not `all`; windowed rollups carry no such figure, so it is never served as `0`), or `unavailable` (the read failed). Always present.
</ResponseField>

<ResponseField name="combo" type="object">
  Present only when the wallet has Combos activity.

  <Expandable title="Combo block fields">
    <ResponseField name="realized_uusdc" type="string">
      Realized PnL from Combos in micro-USDC.
    </ResponseField>

    <ResponseField name="unrealized_uusdc" type="string">
      Unrealized PnL from open Combos in micro-USDC.
    </ResponseField>

    <ResponseField name="fees_uusdc" type="string">
      Fees paid on Combos trades in micro-USDC.
    </ResponseField>

    <ResponseField name="quality" type="string">
      Data quality indicator for Combos attribution.
    </ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="unbooked_activity" type="object" required>
  Disclosure of activity the PnL and positions on this response do **not** include. Always present; never `null`, and never an empty object. Until Polymarket Protocol V2 Binary and NegRisk (module 1 and 2) fills are booked, every figure for a wallet that traded those markets omits those fills, and this block says how many.

  <Expandable title="unbooked_activity fields">
    <ResponseField name="status" type="string">
      `unbooked`: fills exist that the figures omit (see `sources`). `none`: this wallet has no such fills. `unknown`: the source could not be read, so whether fills are omitted is unknown (this is never served as `none`). `not_applicable`: the venue has no such activity (predict.fun has no Protocol V2 modules), or the address is not a valid wallet.
    </ResponseField>

    <ResponseField name="sources" type="array">
      Empty unless `status` is `unbooked`. Then one object: `source` (`pv2_module`), `modules` (`[1, 2]`), `fills` (fills omitted from the figures), `captured_fills` (all module 1/2 fills the wallet made as maker, booked or not), `binary_fills` and `negrisk_fills` (they split `captured_fills`, not `fills`), `first_ts` and `last_ts` (unix seconds of the earliest and latest omitted fill), and `reason`. `fills` can be lower than the true number of omitted fills, never higher: a fill counts as booked when the wallet has a buy or sell book entry in the same transaction (a transfer, convert or redeem entry does not count), so a `none` means no transaction with such a fill lacks one, not proof that every fill is booked.
    </ResponseField>

    <ResponseField name="reason" type="string">
      Present only when `status` is `unknown` or `not_applicable`: why.
    </ResponseField>

    <ResponseField name="as_of" type="integer">
      Unix seconds of the snapshot the answer was read from. Refreshed every five minutes; a fill newer than `as_of` may not be counted yet.
    </ResponseField>
  </Expandable>
</ResponseField>

### Venue semantics

| Venue | `recognized_capital` / `recognized_capital_source` |
| --- | --- |
| Polymarket (`/trader-analytics/traders/{address}`) | Read from the wallet's FIFO fills. `fifo_fills` once every one of the wallet's records carries the convention; `pre_convention` (`null`) until then. |
| predict.fun (`/trader-analytics/predict/traders/{address}`) | The same read and the same shape. The predict.fun engine records no §7.7(b) recognition yet, so it is `null` with `pre_convention` until it does. |

| Field | Polymarket | predict.fun |
| --- | --- | --- |
| `basis` | `net`, `gross` or `unknown` (see the field) | Always `net`: the engine's realized PnL is already net of fees and `?basis=` is neutralized |
| `fees_basis` | Any documented value | Always `engine_net` |
| `fees`, `fees_scope` | All-time fee line, `all_time` | The same; informational only (not netted again) |
| `reference_engine` | Cohort wallets only, `window=all` | Never present |
| `active_positions` | Snapshot of the open-state rollup; `null` when unseeded or quarantined | Snapshot of the same rollup, from FIFO lots; never unseeded |

`unbooked_activity` on predict.fun is always present with `status` `not_applicable`: predict.fun has no Protocol V2 modules, so nothing is captured-but-unbooked there. On Polymarket the count clears by itself when module 1/2 fills are booked (`fills` falls to `0`, `status` to `none`).
