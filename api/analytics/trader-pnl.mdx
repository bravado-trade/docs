<Note>Sign each request with a fresh HMAC signature. The cURL and HTTP header values below are placeholders, not reusable credentials. For runnable signing code, use [request signing examples](/authentication-examples). Python examples use the signed session from that page; Node.js examples use its `bravadoFetch` helper.</Note>


Returns a **gap-free, cumulative-all-time** PnL time series for the wallet,
suitable for plotting an equity curve directly (no client-side stitching
needed). Every point is the wallet's running total **as of that bucket** —
the `window` only selects which slice of the curve comes back; it never
resets the curve to zero. A bucket with no new activity repeats the previous
total, so a wallet with real trading history but nothing inside the
requested window returns a **flat line** at its pre-window level, not an
empty array.

```text
GET https://partner-api.bravadotrade.com/trader-analytics/traders/{address}/pnl
```

<Note>
  **Changed 2026-09-11 — this page describes the default since 2026-09-12.**
  Before 2026-09-11, a bounded `window` (e.g. `30d`) returned a curve
  *relative to window start* (starting near `0`) rather than the wallet's
  cumulative total — and a wallet with no activity inside the window returned
  `series: []` even when it had a long trading history outside it. Both were
  defects: a wallet whose only activity predates the window (e.g. it traded
  heavily in 2024 and nothing since) now correctly renders as a flat line at
  its historical level, and every window's final point now agrees with
  [`GET /traders/{address}`](/api/analytics/overview)'s all-time total. If
  you previously computed your own baseline to splice windows together or to
  backfill history before this endpoint's coverage started, you can remove
  that logic — a single call now returns the complete curve for the window
  you ask for.

  **On 2026-09-12 this became the default rather than the only option**, via
  `?series_kind=cumulative_all_time`. If your integration already adapted to
  (or depends on) the pre-2026-09-11 relative-delta numbers, pass
  `?series_kind=window_delta` to get them back exactly — still gap-filled, so
  a wallet inactive in the window is a flat line at `0.000000`, not `[]`. See
  the `series_kind` parameter below.
</Note>

### Path Parameters

### Query Parameters

<ParamField query="window" default="30d" type="string">
  Time range. Accepted values: `1h`, `4h`, `24h`, `7d`, `30d`, `90d`, `365d`,
  `all` — plus `1y` as an alias of `365d`.
</ParamField>

<ParamField query="interval" default="window-dependent" type="string">
  Bucket resolution: `1h` or `1d` (alias: `resolution`, same values). Default
  depends on `window`: `1h` for `1h`/`4h`/`24h`/`7d`/`30d`, `1d` for
  `90d`/`365d`/`1y`/`all`. There is no finer option (e.g. `5m`) — no data
  source in the platform resolves a wallet's realized PnL more finely than
  the hour, or its open-position mark more finely than the day, so this
  endpoint does not invent resolution it does not have.
</ParamField>

<ParamField query="pnl_type" default="overall" type="string">
  `realized` for the running realized-only curve; `unrealized` for the
  open-position mark series alone (not cumulative — each point is that
  bucket's absolute mark, day-grained); `overall` for the realized curve plus
  the unrealized mark at each bucket.
</ParamField>

<ParamField query="basis" default="net" type="string">
  `net` (fees deducted — exact, integrated over the wallet's whole fee
  history, at both `interval=1d` and `interval=1h`) or `gross`. Until
  2026-09-29 `net` was served as `gross` at `interval=1h`; it is now netted
  from an hourly fee rollup, so every window's final point equals the
  profile's net number. At `interval=1h` the wallet's hourly fee total is
  reconciled with its all-time fees on every request; in the rare case they
  disagree (for example during the nightly fee rebuild) the response is served
  `gross` and says so (`basis: "gross"`, `fees_basis: "unavailable_sub_day"`).
  The response's `basis` is always the one actually applied.
</ParamField>

<ParamField query="series_kind" default="cumulative_all_time" type="string">
  `cumulative_all_time` (default since 2026-09-12): the behavior described on
  this page. `window_delta`: the pre-2026-09-12 numbers — the realized part of each
  point is the sum of the fills since the window start (the baseline before the
  window is `0`, so a wallet with no fills in the window is a flat line at
  `0.000000`, never `[]`). The first point is therefore not `0` when the wallet
  traded in the first bucket. With `pnl_type=overall` the unrealized part is the
  mark-to-market level of the open positions in each bucket (an absolute value,
  not a change since the window start), so an `overall` `window_delta` series
  starts at that level plus the first bucket's realized change. Use this if your integration depends on the older
  relative-delta shape; the response always echoes which one you got.
</ParamField>

### Response

<ResponseField name="trader" type="string" required>
  The wallet, normalised: lowercase with a `0x` prefix, whatever case or prefix you sent.
</ResponseField>

<ResponseField name="window" type="string" required>
  The window applied. The alias `1y` is echoed as `365d`.
</ResponseField>

<ResponseField name="pnl_type" type="string" required>
  The `pnl_type` applied: `overall`, `realized` or `unrealized`.
</ResponseField>

<ResponseField name="basis" type="string" required>
  The fee basis actually applied, `net` or `gross`. See the `basis` parameter.
</ResponseField>

<ResponseField name="interval" type="string" required>
  The bucket resolution actually used (`1h` or `1d`) — the resolved value
  even when you didn't pass `interval`/`resolution`.
</ResponseField>

<ResponseField name="fees_basis" type="string" required>
  Which fees were actually deducted. With the ledger engine's figures, which every probed request is served from, it is `engine_net` (`basis=net`: the engine's realized PnL is already fee-net) or `engine_gross` (`basis=gross`: the fee is added back). Outside that path, for example during a recompute hold, the earlier values apply: `all_time` (exact, `series_kind=
  cumulative_all_time` + `basis=net`, either interval), `window_daily` /
  `window_hourly` (`series_kind=window_delta` + `basis=net` at `interval=1d` /
  `1h` — the window's own fees, cumulative from `0`), `unavailable_sub_day`
  (`basis=net` at `interval=1h` could not be reconciled with the wallet's
  all-time fees, so nothing was deducted and `basis` is `gross`), `none`
  (`basis=gross` was requested), or `engine_net` (predict.fun, whose engine
  realized PnL is already fee-net).
</ResponseField>

<ResponseField name="series_kind" type="string" required>
  Echoes the `series_kind` parameter you sent (or the default,
  `cumulative_all_time`) — a marker so your integration can detect which
  contract a response is on (see the changelog note above) without guessing
  from the numbers.
</ResponseField>

<ResponseField name="unrealized_marks" type="string" required>
  How the series' unrealized component is sourced: `none` (`pnl_type=realized`
  — no unrealized component), `day_grained` (`interval=1d` — an exact daily
  mark), `day_grained_carried_forward` (`interval=1h` — no hourly
  unrealized-mark source exists, so the day's mark is repeated across its
  hours rather than interpolated).

  In every case the carried-forward mark has a staleness bound: once a mark
  is older than that bound, points that would otherwise carry it forward
  serve `0` for the unrealized component instead — a wallet whose
  position-marking rollup has stopped updating is treated as "no current
  mark," never as "still holding whatever it last held."
</ResponseField>

<ResponseField name="empty_reason" type="string">
  Present **only** when `series` is empty: `no_wallet_history` for a wallet
  this platform has never observed any activity for. A wallet with real
  history but nothing inside the requested window is **not** empty — see
  above — so this field is otherwise omitted.
</ResponseField>

<ResponseField name="series" type="array" required>
  One point per bucket, gap-free, from window start to now. Each point has two fields: `ts` (integer) is the Unix timestamp of the bucket boundary, and `pnl` (string) is the wallet's cumulative PnL **as of this bucket** (a decimal string in USDC): its running total, not a value relative to window start.
</ResponseField>

<ResponseField name="exchange_surplus" type="object" required>
  The wallet's exchange-surplus income over the window: income outside trading PnL, served beside the series and not inside it. Fields: `status` (`known` or `unknown`), `amount_uusdc` (integer micro-USDC), `amount` (decimal string), `count`, `classification` (`income_outside_trading_pnl`), `in_realized_pnl` (`false` means the amount is on top of the series, `true` means it is already inside it), `scope` (`all_time` or `window:<window>`), `through_block` (rows above this block are not derived yet), `coverage` and `source`. When `status` is `unknown` the amount fields are `null` and `unknown_reason` is present: an unknown amount is never served as `0`. Read `coverage` before treating a `0` as complete.
</ResponseField>

<ResponseField name="third_party_fees" type="object" required>
  The wallet's redemption-service and collector fees over the window: an expense outside trading PnL, beside the series and never inside it (`in_realized_pnl` is always `false`). Same fields as `exchange_surplus`, with `classification` `expense_outside_trading_pnl`. Only registered fee collectors are counted, as `coverage` states.
</ResponseField>

<ResponseField name="book_status" type="string" required>
  `ok`, or `quarantined` when the wallet's book stopped at a transfer leg that could not be booked. A quarantined response also carries `unknown_from_ts` (and, where dated, `unknown_from_block` and `quarantine_reason`): every point at or after `unknown_from_ts` is the last good state carried forward, not a current figure.
</ResponseField>

<ResponseField name="unbooked_activity" type="object" required>
  Disclosure of activity the series does **not** include. Always present; never `null`, and never an empty object. Until Polymarket Protocol V2 Binary and NegRisk (module 1 and 2) fills are booked, every figure for a wallet that traded those markets omits those fills, and this block says how many.

  <Expandable title="unbooked_activity fields">
    <ResponseField name="status" type="string">
      `unbooked`: fills exist that the figures omit (see `sources`). `none`: this wallet has no such fills. `unknown`: the source could not be read, so whether fills are omitted is unknown (this is never served as `none`). `not_applicable`: the venue has no such activity (predict.fun has no Protocol V2 modules), or the address is not a valid wallet.
    </ResponseField>

    <ResponseField name="sources" type="array">
      Empty unless `status` is `unbooked`. Then one object: `source` (`pv2_module`), `modules` (`[1, 2]`), `fills` (fills omitted from the figures), `captured_fills` (all module 1/2 fills the wallet made as maker, booked or not), `binary_fills` and `negrisk_fills` (`captured_fills` by module), `first_ts` and `last_ts` (unix seconds of the earliest and latest omitted fill), and `reason`. `fills` can be lower than the true number of omitted fills, never higher: a fill counts as booked when the wallet has any book entry in the same transaction, so a `none` means no transaction with such a fill lacks one, not proof that every fill is booked.
    </ResponseField>

    <ResponseField name="reason" type="string">
      Present only when `status` is `unknown` or `not_applicable`: why.
    </Resp

<Note>
  The **last point of every window's series is the same number**: the
  wallet's current all-time total for the requested `pnl_type`/`basis`. That
  also equals [`GET /traders/{address}`](/api/analytics/overview)'s
  `realized_pnl` (for `pnl_type=realized`) or `total_pnl` (for
  `pnl_type=overall`), same `basis` — a useful sanity check if you're
  reconciling a chart against the profile card next to it.
</Note>

## Errors

| Status | Code | Meaning |
| --- | --- | --- |
| `400` | none | `window`, `interval`, `pnl_type`, `basis` or `series_kind` is not one of its allowed values. The body is `{"error": "..."}` without a `code`. |

### Example: hourly resolution over the last 24 hours

<CodeGroup>

```bash cURL
curl -G https://partner-api.bravadotrade.com/trader-analytics/traders/0xabc.../pnl \
  -H "X-BRAVADO-API-KEY: $BRAVADO_API_KEY" \
  -H "X-BRAVADO-TIMESTAMP: <unix-ms>" \
  -H "X-BRAVADO-SIGNATURE: <signature-for-this-request>" \
  -d window=24h \
  -d interval=1h \
  -d pnl_type=overall
```

```json Response (abbreviated)
  "trader": "0xabc...",
  "window": "24h",
  "interval": "1h",

```

</CodeGroup>

window_delta`, the flat line is at `0.000000` (delta from window start, its
pre-2026-09-12 meaning) instead of the wallet's all-time total, and it is
still a full gap-filled series, never `[]`:
