When you submit a `PEGGED`, `TWAP`, `ICEBERG`, `STOP_LOSS`, `TRAILING_STOP` or `TRAILING_BUY` order, Bravado returns a `record_id` instead of a CLOB `order_id`. These long-running strategy records are tracked separately from the CLOB order book. Use the strategies endpoints to monitor their lifecycle and cancel them before they complete or trigger.

---

## GET /v2/trade/strategies

Returns all managed strategy records on your account. You can filter by status to focus on live strategies or review historical executions.

### Query parameters

<ParamField query="status" type="string">
  Filter by strategy status. Accepted values, upper-case:
  - `ACTIVE`, running, or armed and waiting for its trigger.
  - `PAUSED`, `PEGGED` only: temporarily not quoting. `last_error` says why.
  - `COMPLETED`, finished. Not always fully filled: see [Order and strategy states](/api/trade/order-states).
  - `CANCELED`, cancelled by you, or expired (an `ICEBERG` past `expires_at`, an expired `PEGGED`).
  - `ERROR`, stopped by a failure. `last_error` holds the reason.
</ParamField>

### Response

<ResponseField name="strategies" type="array">
  Array of strategy objects.

  <Expandable title="strategy fields">
    <ResponseField name="id" type="string">
      The `record_id` of this strategy. Use this value with `DELETE /v2/trade/strategies/{id}`.
    </ResponseField>
    <ResponseField name="type" type="string">
      Strategy type: `PEGGED` | `TWAP` | `ICEBERG` | `STOP_LOSS` | `TRAILING_STOP` | `TRAILING_BUY`.
    </ResponseField>
    <ResponseField name="status" type="string">
      Current lifecycle status: `ACTIVE` | `PAUSED` | `COMPLETED` | `CANCELED` | `ERROR`.
    </ResponseField>
    <ResponseField name="side" type="string">
      `"buy"` or `"sell"`.
    </ResponseField>
    <ResponseField name="token_id" type="string">
      Outcome token address this strategy operates on.
    </ResponseField>
    <ResponseField name="condition_id" type="string">
      Polymarket condition ID. Present for `PEGGED` and stop orders.
    </ResponseField>
    <ResponseField name="total_size" type="string">
      Total targeted by this strategy: shares for `TWAP`, `ICEBERG`, `STOP_LOSS` and `TRAILING_STOP`; a USD budget for `PEGGED` and `TRAILING_BUY`.
    </ResponseField>
    <ResponseField name="filled_size" type="string">
      Filled so far, in the same unit as `total_size` (USD for `PEGGED`). `null` on a stop that has not sold.
    </ResponseField>
    <ResponseField name="price" type="string">
      Reference or limit price as a decimal probability. For stops, this is the trigger price.
    </ResponseField>
    <ResponseField name="trailing_offset_pct" type="string">
      Trail distance as a percentage. Present for `TRAILING_STOP` strategies only.
    </ResponseField>
    <ResponseField name="high_water_mark" type="string">
      Current high-water mark price tracked by a `TRAILING_STOP`.
    </ResponseField>
    <ResponseField name="created_at" type="number">
      Unix timestamp, in seconds, when the strategy was created.
    </ResponseField>
  </Expandable>
</ResponseField>

<Note>
  `STOP_LOSS`, `TRAILING_STOP` and `TRAILING_BUY` records appear only here, before and after they trigger. A stop sells with one all-or-nothing market order that never rests, so it never appears on `GET /v2/trade/orders/open`. A stop created with `status: "PENDING"` shows `ACTIVE` here. See [Stop-loss and take-profit rules](/api/trade/stop-loss-rules).
</Note>

## DELETE /v2/trade/strategies/{id}

Cancels a managed strategy by its `record_id`. The operation is idempotent, cancelling an already-terminal strategy (`COMPLETED`, `CANCELED`, `ERROR`) returns the current record without error.

**Required headers**

| Header | Value |
|--------|-------|
| HMAC headers | [Public key, timestamp and signature](/authentication) |
| `Idempotency-Key` | Unique string (UUID recommended) |

### Path parameters

<ParamField path="id" type="string" required>
  The `record_id` of the strategy to cancel (e.g. `rec_twap_abc123`).
</ParamField>

### Response

<ResponseField name="id" type="string">
  The strategy record ID.
</ResponseField>

<ResponseField name="type" type="string">
  Strategy type.
</ResponseField>

<ResponseField name="status" type="string">
  Final status after the cancellation attempt, `CANCELED` on success, or the existing terminal status if already complete.
</ResponseField>

### Example

<CodeGroup>

```http Request
DELETE /v2/trade/strategies/rec_twap_abc123
X-BRAVADO-API-KEY: <public-key>
X-BRAVADO-TIMESTAMP: <timestamp-ms>
X-BRAVADO-SIGNATURE: <signature-for-this-request>
Idempotency-Key: c9d0e1f2-a3b4-5678-2cde-678901234508
```

```json Response
{
  "id": "rec_twap_abc123",
  "type": "TWAP",
  "status": "CANCELED"
}
```

</CodeGroup>

<Warning>
  A `STOP_LOSS` or `TRAILING_STOP` can only be cancelled before it triggers. Once the trigger is hit it is being executed: the cancel fails, and there is no resting order to cancel instead. A stop in `ERROR` is answered with `ERROR` and is not cancelled, even if the engine still has attempts left. See [Stop-loss and take-profit rules](/api/trade/stop-loss-rules#cancelling).
</Warning>

## Where to find each order type

Different order types surface on different endpoints depending on their current state. Use this table to locate any order after submission:

| Order Type | Returns on submission | Live tracking endpoint |
|---|---|---|
| `LIMIT` | `order_id` | `GET /v2/trade/orders/open` |
| `MARKET` | `order_id` | Never rests (fills or is cancelled at once; check `/activity`) |
| `TAKE_PROFIT` | `order_id` | `GET /v2/trade/orders/open` (`is_take_profit: true`) |
| `STOP_LOSS` | `record_id` | `GET /v2/trade/strategies` only, before and after it triggers |
| `TRAILING_STOP` | `record_id` | `GET /v2/trade/strategies` |
| `TRAILING_BUY` | `record_id` | `GET /v2/trade/strategies` |
| `TWAP` | `record_id` | `GET /v2/trade/strategies` |
| `ICEBERG` (parent) | `record_id` | `GET /v2/trade/strategies` |
| `ICEBERG` (active slice) | child `order_id` | `GET /v2/trade/orders/open` |
| `PEGGED` | `record_id` | `GET /v2/trade/strategies` |

<Tip>
  For bracket orders (take-profit and stop-loss attached to a `LIMIT` or `MARKET` buy), the `brackets` field on the order response carries `take_profit.order_id` for the resting take-profit and `stop_loss.id` (the `record_id`) for the stop-loss. The two legs are not linked: when one fills, cancel the other yourself.
</Tip>
