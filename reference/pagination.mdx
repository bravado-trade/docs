Bravado uses two distinct pagination patterns depending on the nature of the data being returned. Most list endpoints use classic offset/limit pagination, which is simple to implement and supports random access. Trade history and activity timeline endpoints use cursor-based pagination, which is more efficient for large, append-only datasets and guarantees you won't miss records if new data arrives between pages.

## Offset/limit pagination

For most list endpoints, you control pagination using `limit` and `offset` query parameters. The response includes metadata fields that tell you how many total records exist and whether there are more pages to fetch.

**Endpoints that use offset/limit:**
- `GET /leaderboard`
- `GET /traders/{address}/positions`
- `GET /v2/trade/positions`
- `GET /v2/trade/combo/positions`
- PMWAS statement endpoints (with `r1_limit` / `r1_offset`, see [PMWAS R1 pagination](#pmwas-r1-pagination)); `GET /traders/{address}/statements/r1` pages by cursor

**Example request:**

```http
GET /traders/0xabc.../positions?limit=100&offset=0 HTTP/1.1
X-BRAVADO-API-KEY: <public-key>
X-BRAVADO-TIMESTAMP: <unix-ms>
X-BRAVADO-SIGNATURE: <signature-for-this-request>
```

**Example response:**

```json
{
  "positions": [...],
  "total": 342,
  "limit": 100,
  "offset": 0,
  "has_more": true
}
```

Use `total`, `limit`, and `offset` to determine whether another page exists. Stop when `offset + limit >= total` (or when `has_more` is `false`).

**Python iteration example:**

```python
offset = 0
limit = 100

while True:
    resp = get(f"/traders/{address}/positions?limit={limit}&offset={offset}")
    data = resp.json()

    process(data["positions"])

    if offset + limit >= data["total"]:
        break

    offset += limit
```

<Tip>
Request the largest page size your use case allows to minimise the number of round trips. See the [page size limits table](#page-size-limits) below for per-endpoint maximums.
</Tip>

## Cursor-based pagination

Trade history and activity timeline endpoints use cursor-based pagination. Instead of an offset, you pass a cursor value returned by the previous response to fetch the next page. This approach is safe against data mutations between pages and handles high-volume datasets efficiently.

### Trade history cursors

`GET /traders/{address}/trades` and `GET /trades` (default, `TRADE` and `SETTLE` feeds) page by the key `(block_number, log_index, tx_hash, token_id)`, the order the rows are served in. Pass the five `next_cursor*` fields of the previous response back as the cursor:

| Send | From the response | Notes |
|------|-------------------|-------|
| `cursor_ts` | `next_cursor` | |
| `cursor_block` | `next_cursor_block` | Required with any cursor. `0` means no trade row served yet (for example a page of only redemptions): the response then omits `next_cursor_log_idx`, `next_cursor_tx` and `next_cursor_token`, and you send just `cursor_ts` and `cursor_block=0`. |
| `cursor_log_idx` | `next_cursor_log_idx` | Required when `cursor_block > 0`. `0` is a real value. |
| `cursor_tx` | `next_cursor_tx` | Required when `cursor_block > 0`. |
| `cursor_token` | `next_cursor_token` | Required when `cursor_block > 0`. |

When `next_cursor` is `0`, you have reached the end. An incomplete cursor, including a bare `cursor_ts`, is `400 invalid_cursor`. The key is total, so a page boundary between blocks that share a timestamp neither skips nor repeats rows, on Polymarket and on predict.fun alike.

**Python iteration example:**

```python
cursor = {}

while True:
    resp = get(f"/traders/{address}/trades", params={"limit": 100, **cursor})
    data = resp.json()

    process(data["trades"])

    if not data["next_cursor"]:
        break

    # pass back every field the response carries; the key fields are absent on a "no trade row yet" page
    cursor = {"cursor_ts": data["next_cursor"], "cursor_block": data["next_cursor_block"]}
    for src, dst in (("next_cursor_log_idx", "cursor_log_idx"), ("next_cursor_tx", "cursor_tx"), ("next_cursor_token", "cursor_token")):
        if src in data:
            cursor[dst] = data[src]
```

`type=SPLIT`, `MERGE` and `CONVERSION` use the key `(block_number, log_index, token_id)`: pass back `cursor_ts`, `cursor_block`, `cursor_log_idx` and `cursor_token` (no `cursor_tx`).

<Note>
Send every field the response carries, unchanged. `cursor_log_idx=0` is a real value, not an omitted one.
</Note>

### Activity timeline cursor

`GET /v2/trade/activity` uses an opaque string cursor rather than a timestamp integer. Treat the `next_cursor` value as opaque, do not parse or construct it manually.

**Example request (first page):**

```http
GET /v2/trade/activity?limit=50 HTTP/1.1
X-BRAVADO-API-KEY: <public-key>
X-BRAVADO-TIMESTAMP: <unix-ms>
X-BRAVADO-SIGNATURE: <signature-for-this-request>
```

**Example response:**

```json
{
  "activity": [...],
  "next_cursor": "eyJvZmZzZXQiOjUwfQ=="
}
```

**Example request (next page):**

```http
GET /v2/trade/activity?limit=50&cursor=eyJvZmZzZXQiOjUwfQ== HTTP/1.1
X-BRAVADO-API-KEY: <public-key>
X-BRAVADO-TIMESTAMP: <unix-ms>
X-BRAVADO-SIGNATURE: <signature-for-this-request>
```

When `next_cursor` is `null` or absent, you have fetched all available activity.

**Python iteration example:**

```python
cursor = None

while True:
    params = {"limit": 50}
    if cursor:
        params["cursor"] = cursor

    resp = get("/v2/trade/activity", params=params)
    data = resp.json()

    process(data["activity"])

    cursor = data.get("next_cursor")
    if not cursor:
        break
```

## PMWAS R1 pagination

The PMWAS statements endpoint has a nested pagination layer for R1 disposition rows within each statement. Use `r1_limit` and `r1_offset` to page through disposition rows independently of the top-level statement pages.

```http
GET /traders/{address}/statements?limit=10&offset=0&r1_limit=500&r1_offset=0 HTTP/1.1
X-BRAVADO-API-KEY: <public-key>
X-BRAVADO-TIMESTAMP: <unix-ms>
X-BRAVADO-SIGNATURE: <signature-for-this-request>
```

Check `has_more_r1` in the response to determine whether additional R1 rows exist for the current statement page.

For direct access to R1 rows without the parent statement wrapper, use the standalone endpoint, which pages by cursor. Pass each response's `next_cursor` (`<batch_block>:<row_seq>`) back as `cursor` until `has_more` is `false`. `offset` is deprecated and limited to `100000` (`400 offset_too_deep`). If the wallet's R1 is rebuilt mid-walk, the next request is `409 stale_cursor`: restart from the first page.

```http
GET /traders/{address}/statements/r1?limit=500 HTTP/1.1
X-BRAVADO-API-KEY: <public-key>
X-BRAVADO-TIMESTAMP: <unix-ms>
X-BRAVADO-SIGNATURE: <signature-for-this-request>
```

## Page size limits

Requesting more than the maximum allowed limit for an endpoint will result in a `400 Bad Request`. Use these maximums as your target batch size when iterating through large datasets.

| Endpoint | Max `limit` |
|----------|------------|
| `GET /leaderboard` | 500 |
| `GET /traders/{address}/positions` | 1000 |
| `GET /traders/{address}/trades` | 500 |
| `GET /v2/trade/positions` | 500 |
| `GET /v2/trade/activity` | 200 |
| `GET /v2/trade/combo/positions` | 500 |
| `GET /traders/{address}/statements` (R1 rows) | 5000 |
| `GET /traders/{address}/statements/r1` | 5000 |
