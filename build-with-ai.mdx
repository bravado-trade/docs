Build prediction-market agents, research systems, trading bots, and AI-native applications with Bravado. Bravado is prediction-market infrastructure, and an AI application reaches different parts of it through different interfaces: an MCP server for agent-native data access, WebSockets for realtime market state, REST APIs for programmatic analytics and execution, and machine-readable docs for your coding assistant.

This page is the map. It explains which product to reach for, in what situation, and how they fit together. For the deep reference on any one product, follow its link.

## Which interface do I use?

| I want my AI to... | Use |
| --- | --- |
| Query trader intelligence directly from an agent | [MCP Server](/products/mcp-server) |
| Consume realtime market data (order books, trades, prices) | [Market Data / WebSockets](/products/market-data) |
| Query positions, PnL, wallets, or historical trader data over REST | [Trader Data API](/products/data-api) |
| Execute trades | [Trade API](/products/trade-api) |
| Understand market resolution and settlement | [UMA API](/products/uma-api) |
| Understand the Bravado docs while coding | [llms.txt / llms-full.txt](#build-faster-with-ai-coding-tools) |

<Note>
  **Research and execution are separate surfaces.** Agents *read* intelligence through the MCP Server and the Trader Data API, and *act* only through the Trade API. The MCP Server is read-only and never places a trade or moves funds. Keep that boundary in your architecture and you keep it in your risk model.
</Note>

## Give your agent direct access to prediction-market intelligence

Bravado hosts a **Model Context Protocol (MCP)** server, so an MCP-compatible agent (Claude.ai, Claude Desktop, Claude Code, or a custom runtime) can query Bravado's trader intelligence directly, with no REST wrapper to write and no tools to hand-define. You connect once with OAuth and the agent gets a curated toolset.

Supported today:

- `get_leaderboard`, traders ranked by realized PnL or volume
- `get_trader_profile`, a full performance profile for any public address
- `get_trader_pnl_series`, PnL over time
- `get_trader_positions` and `get_trader_trades`, holdings and activity
- `get_trader_categories`, PnL and volume by market category
- `get_reconciliation_certificate`, a consistency proof for a wallet's statement
- `run_sql`, read-only SQL against curated warehouse views

<Warning>
  **The MCP Server is read-only, permanently.** It cannot place, cancel, or modify an order, and it cannot move funds. It is for querying data and analytics. When an agent needs to act, it uses the [Trade API](/products/trade-api), described below.
</Warning>

Connect a client in one line:

```bash
claude mcp add --transport http bravado https://mcp.bravadotrade.com/mcp
```

See the [MCP Server reference](/products/mcp-server) for the full tool list, OAuth authorization flow, scopes, and rate limits.

## Give your agent realtime market context

When an agent or application needs to know what the market is doing *right now*, stream it from Bravado's [Market Data](/products/market-data) WebSockets rather than polling REST. Two public feeds are available:

- **Live trades**, `wss://partner-api.bravadotrade.com/trade-feed/ws`, a stream of every fill across all markets, each enriched with the trader's name and wallet. See the [Live Trades reference](/api/market-data/trade-feed).
- **Order books**, `wss://partner-api.bravadotrade.com/orderbook-feed/ws?assetId=<id>`, live book snapshots, incremental price updates, and best bid/ask for any outcome token. See the [Order Books reference](/api/market-data/order-book).

The two feeds link together by `assetId`: watch the trade stream to see where activity is, then subscribe to the order book for those tokens. The `trader` on each trade also links to [Trader Data](/products/data-api), so an agent can pull a wallet's PnL and history the moment it sees it trade.

<Note>
  Market Data is realtime infrastructure. The MCP Server is **not** a substitute for it: MCP answers point-in-time analytical questions, WebSockets deliver a live feed. Agents that trade or track markets in realtime need the WebSocket feeds.
</Note>

## Query trader analytics over REST

When an application needs programmatic access to trader analytics, on its own schedule rather than through an agent's tool loop, use the [Trader Data API](/products/data-api). It is the same engine behind the MCP Server, exposed as signed REST:

- wallet positions, PnL, and cost basis
- trade history and wallet activity
- leaderboards, win rate, and trader performance

This works for AI systems and ordinary applications alike. Reach for it when you want a normal HTTP integration, a backfill job, or a dashboard, rather than an agent-native tool surface.

## Let your application act

If an AI-powered application needs to trade, it executes through the [Trade API](/products/trade-api), never through MCP. The Trade API covers the full order lifecycle: place and manage orders, eight order types including TWAP and bracket orders, positions, and balances. Every mutating call takes an `Idempotency-Key`, so an agent that retries on failure cannot double-execute. See [Idempotency](/reference/idempotency).

The clean separation to hold in your head:

```text
MCP Server / Trader Data API  →  research and context
Market Data (WebSockets)      →  realtime market state
Trade API                     →  execution
UMA API                       →  resolution context
```

## Understand resolution and settlement

An agent evaluating market lifecycle or settlement risk needs to tell a *concluded* event from a *settled, redeemable* position. The [UMA API](/products/uma-api) exposes how Polymarket markets resolve through UMA's Optimistic Oracle: proposals, disputes, and final outcomes. Use it so an agent does not book PnL on a position that cannot yet be redeemed.

<Note>
  The UMA API endpoint reference is still being written. Until it lands, resolution state has to be inferred from position data. See [UMA API](/products/uma-api).
</Note>

## Architecture examples

How the products compose for common AI applications.

### Research agent

Reads intelligence, takes no action. All read-only.

```text
MCP Server
   ↓
Trader PnL · Positions · Leaderboard · Trade history
   ↓
LLM / Agent
```

### Trading agent

Reacts to realtime market state, then executes through the Trade API.

```text
Market Data / WSS
        ↓
Realtime market state
        ↓
Agent strategy
        ↓
Trade API
        ↓
Execution

Trader Data API  →  historical context
UMA API          →  resolution context
```

### Prediction-market copilot

Combines live markets, intelligence, resolution, and optional execution.

```text
MCP        →  trader intelligence
WSS        →  realtime markets
UMA API    →  resolution
Trade API  →  optional execution
```

## Build faster with AI coding tools

Give Claude Code, Cursor, Windsurf, or any coding assistant the full Bravado docs as context so it writes correct integration code.

Every page on this site is available as machine-readable Markdown:

- Append `.md` to any docs URL to get the raw source, for example `https://docs.bravadotrade.com/quickstart.md`.
- `https://docs.bravadotrade.com/llms.txt` lists every page for LLM crawlers.
- `https://docs.bravadotrade.com/llms-full.txt` concatenates the entire docs site into one file, suitable for pasting into a long-context model.

For **Cursor**, **Windsurf**, or **Claude Code**, add the docs to the workspace context:

```text
https://docs.bravadotrade.com/llms-full.txt
```

The assistant then has the full API surface, concepts, and guides in context when generating Bravado code.

Every page also has a **Copy** button in the contextual menu: *Copy page as Markdown*, *View as Markdown*, *Open in ChatGPT*, and *Open in Claude*. Use those when you want a model to reason about one specific page.

## Safety patterns for autonomous agents

When wiring an agent to Bravado's trading endpoints:

1. **Cap notional per tool call.** Enforce the cap in your tool wrapper, not the prompt.
2. **Require idempotency at the tool layer.** Generate the UUID inside the tool. See [Idempotency](/reference/idempotency).
3. **Sandbox first.** Test agents against a follower wallet with a small balance.
4. **Log every call.** Every mutating call includes an idempotency key. Log per-agent, per-session for review.

See the [AI agents use case](/use-cases/ai-agents) for a worked example.
