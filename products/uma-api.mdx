Polymarket markets do not settle themselves. When a market's event concludes, the outcome has to be reported on-chain and accepted before holders can redeem winning shares. Polymarket uses [UMA](https://uma.xyz)'s Optimistic Oracle (V2) for that step, and the Bravado UMA API exposes the resolution lifecycle as both **queryable data** (REST) and a **realtime stream** (WebSocket).

<Info>
  The UMA REST endpoints and stream are served from `partner-api.bravadotrade.com`,
  the same host as the rest of the Bravado API. UMA resolution is public
  market data, so these endpoints need **no authentication** — no token, no key.
  Coverage today is Polymarket.
</Info>

## Why Bravado over reading the chain

Resolution data exists on-chain, so this is not about access. It is about not having to build an indexer to answer a question every prediction market application eventually has to answer: **is this position actually finished?**

| | Reading the chain yourself | Bravado UMA API |
| --- | --- | --- |
| Setup | Index the UMA oracle + adapter events yourself | Query an endpoint / subscribe to a stream |
| Lifecycle state | Decode `ProposePrice` / `DisputePrice` / `Settle` logs | `stage` returned as data |
| Answer | Interpret the raw `int256` price | `answer` classified (`yes` / `no` / `50-50` / `too-early`) |
| Correlation to positions | Map oracle events back to your holdings | `condition_id` aligned with the same market identifiers as the rest of Bravado |
| Freshness | Wait for the confirmed resolution | The **proposal** streams from the mempool ~1 s **before** it is mined (`seen_pending`), then confirms with the block |

The practical payoff is that a "concluded" event and a redeemable position stop being the same thing in your data model. An application that conflates them will show users balances they cannot access, and book PnL that has not been realised.

## How UMA resolution works

Bravado decodes UMA's Optimistic Oracle V2 directly, so you see each step as it happens.

<Steps>
  <Step title="Proposal">
    Once the event concludes, a proposer posts the outcome to the oracle with a bond. This is the `proposed` stage; `answer` carries the proposed result. Bravado decodes the proposer's transaction straight from the mempool, so the proposal is delivered with `"seen_pending":true` ~0.3–1.4 s before it is mined, then a confirming frame follows with the `block` and `tx`.
  </Step>
  <Step title="Challenge window">
    The proposal stays open for a fixed liveness period. If nobody disputes it, it settles automatically on the proposed answer.
  </Step>
  <Step title="Dispute (optional)">
    Any party may dispute within the window by posting their own bond (`disputed` stage). A disputed request escalates to UMA's token-holder vote rather than settling on the proposer's word.
  </Step>
  <Step title="Settlement">
    The final answer is written on-chain (`settled` stage, with the `payout`). Winning outcome tokens become redeemable at \$1; losing tokens go to \$0.
  </Step>
</Steps>

<Warning>
  A market whose event has visibly concluded is not necessarily settled. Always confirm `settled: true` before treating a position as realized — an undisputed proposal can still be disputed until its challenge window closes.
</Warning>

## Identifiers

Every lifecycle record carries two ids:

- **`question_id`** — `keccak256(ancillaryData)`, the UMA adapter's question id. This is the stable, exact key for a resolution.
- **`condition_id`** — the CTF condition id used everywhere else in Bravado to identify the market. Use it to join resolution state to positions and trades.

The `answer` field classifies the oracle's `int256` price: `yes`, `no`, `50-50`, `too-early`, or `other`; `price_raw` preserves the exact value.

## REST — query resolution state

Base URL: `https://partner-api.bravadotrade.com`. No authentication required. JSON; ids are hex, `payout` is an integer micro-USDC string.

### `GET /uma/question`

The full lifecycle of one question.

```text
GET https://partner-api.bravadotrade.com/uma/question?id=<0x questionId>
```

<ParamField query="id" type="string" required>
  The `0x` 32-byte `question_id`.
</ParamField>

<ResponseField name="question_id" type="string">Hex question id (`keccak256(ancillaryData)`).</ResponseField>
<ResponseField name="condition_id" type="string">Hex CTF condition id for the market.</ResponseField>
<ResponseField name="title" type="string">Human-readable market question (from the ancillary data).</ResponseField>
<ResponseField name="answer" type="string">Latest answer: `yes` · `no` · `50-50` · `too-early` · `other`.</ResponseField>
<ResponseField name="settled" type="boolean">Whether the resolution has finalized on-chain.</ResponseField>
<ResponseField name="proposed" type="object">
  <Expandable title="stage fields">
    <ResponseField name="proposer" type="string">Address that posted the proposal.</ResponseField>
    <ResponseField name="answer" type="string">Answer classified from the proposed price.</ResponseField>
    <ResponseField name="price_raw" type="string">Exact `int256` price, hex.</ResponseField>
    <ResponseField name="request_ts" type="integer">Oracle request timestamp (unix seconds).</ResponseField>
    <ResponseField name="block" type="integer">Polygon block.</ResponseField>
    <ResponseField name="tx" type="string">Transaction hash.</ResponseField>
    <ResponseField name="log_index" type="integer">Log index within the block.</ResponseField>
    <ResponseField name="seen_pending" type="boolean">Present and `true` while this proposal/dispute is known only from the mempool (`block` is `0`); cleared once mined.</ResponseField>
  </Expandable>
</ResponseField>
<ResponseField name="disputed" type="object">Same shape as `proposed`, plus `disputer`. Present only if the proposal was disputed.</ResponseField>
<ResponseField name="settled_at" type="object">Same shape, plus `payout` (micro-USDC string). Present once `settled`.</ResponseField>
<ResponseField name="updated_ms" type="integer">When Bravado last updated this record (unix ms).</ResponseField>

### `GET /uma/market`

The same record, keyed by the market's CTF condition id.

```text
GET https://partner-api.bravadotrade.com/uma/market?condition_id=<0x conditionId>
```

<ParamField query="condition_id" type="string" required>The `0x` 32-byte CTF condition id.</ParamField>

### `GET /uma/recent`

Recently-updated questions, newest first — a feed of live proposals, disputes, and settlements.

```text
GET https://partner-api.bravadotrade.com/uma/recent?stage=settled&limit=100
```

<ParamField query="stage" type="string">Filter by current stage: `proposed` · `disputed` · `settled`. Omit for all.</ParamField>
<ParamField query="limit" type="integer" default="100">Max records (1–500).</ParamField>

<ResponseField name="questions" type="array">Array of question records (same shape as `GET /uma/question`).</ResponseField>
<ResponseField name="count" type="integer">Number of records returned.</ResponseField>

## WebSocket — stream the lifecycle

For push instead of poll, connect to `wss://partner-api.bravadotrade.com/uma/ws`.
No subscription message and no authentication are needed — every Polymarket
proposal, dispute, and settlement is pushed to you as a `uma` frame. To follow a
single market, filter on `question_id` (or `condition_id`) client-side.

<CodeGroup>

```javascript JavaScript
const ws = new WebSocket("wss://partner-api.bravadotrade.com/uma/ws");
ws.onmessage = (e) => {
  const f = JSON.parse(e.data);
  if (f.type === "uma") {
    console.log(`${f.stage} — ${f.title} → ${f.answer}`);
  }
};
```

```python Python
import json, asyncio, websockets  # pip install websockets

async def main():
    url = "wss://partner-api.bravadotrade.com/uma/ws"
    async for ws in websockets.connect(url):
        async for msg in ws:
            f = json.loads(msg)
            if f.get("type") == "uma":
                print(f["stage"], "—", f.get("title"), "→", f["answer"])

asyncio.run(main())
```

</CodeGroup>

The `uma` frame carries `stage`, `answer`, `question_id`, `condition_id`, `proposer`, `disputer`, `price_raw`, `payout`, `request_ts`, `title`, `block`, `tx`, and `log_index`. A proposal or dispute decoded from the mempool carries `"seen_pending":true` with `block:0`; the same `question_id` is re-sent once mined with the real `block`/`tx` (the pending→mined pair). Settlements are mined-only and never carry `seen_pending`.
